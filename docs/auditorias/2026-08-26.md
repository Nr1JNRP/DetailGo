## Detalhamento dos Achados

### 1. Escalação de papel e alteração irrestrita de perfil em `users/{userId}`
- **Severidade:** ALTO
- **Arquivo afetado:** `firestore.rules` (linhas 91–102)
- **Comportamento vulnerável:** A regra `match /users/{userId} { allow read, write: if isSignedIn() && request.auth.uid == userId; }` permite que qualquer usuário autenticado leia e grave qualquer campo em seu próprio documento em `/users/{userId}` via SDK cliente do Firestore. Um usuário com perfil de cliente (`customer`) pode atualizar o campo `role` para `'owner'` ou associar arbitrariamente `shopId` no seu documento de perfil.
- **Impacto possível:** Embora o acesso a dados de outros estabelecimentos na árvore `/shops/{shopId}` no Firestore permaneça protegido pelas regras de segurança (que validam `shops/{shopId}.ownerId`), a aplicação móvel confia nos dados de `users/{userId}` (`ShopContext` e `RootNavigator`) para gerenciar a navegação e autorização no cliente. Um usuário mal-intencionado pode alterar seu perfil para acessar a interface do painel do proprietário no aplicativo.
- **Correção recomendada:** Restringir os campos alteráveis no `update` da coleção `users/{userId}` em `firestore.rules` (por exemplo, impedindo a modificação dos campos `role` e `shopId` diretamente pelo cliente, exigindo `request.resource.data.diff(resource.data).affectedKeys().hasAny(['role', 'shopId']) == false`), ou delegar a alteração de papel e criação de lojas a Cloud Functions protegidas via Admin SDK.
- **Cabe teste de regressão:** Sim. Teste em `firestore-tests/` tentando atualizar o campo `role` como um usuário autenticado comum e garantindo que a operação é negada pelo Firestore.

### 2. Leitura irrestrita da coleção de registros financeiros (`/payments/{paymentId}`)
- **Severidade:** MÉDIO
- **Arquivo afetado:** `firestore.rules` (linhas 104–109)
- **Comportamento vulnerável:** A regra para a coleção de pagamentos define `match /payments/{paymentId} { allow read: if isSignedIn(); allow write: if false; }`. Isso permite que QUALQUER usuário autenticado na plataforma (incluindo clientes comuns) liste ou leia todos os documentos gravados em `/payments/{paymentId}`.
- **Impacto possível:** Exposição de metadados financeiros de terceiros e de estabelecimentos (como `paymentId`, `shopId`, `shopName`, `amount`, status do pagamento e timestamps), violando o isolamento do tenant e a privacidade das transações.
- **Correção recomendada:** Alterar a permissão de leitura em `firestore.rules` para que apenas o proprietário do estabelecimento correspondente (`isShopOwner(resource.data.shopId)`) consiga ler o registro de pagamento:
  ```doc
  allow read: if isSignedIn() && isShopOwner(resource.data.shopId);
  ```
- **Cabe teste de regressão:** Sim. Teste em `firestore-tests/` validando que um usuário cliente ou dono de outra loja não consegue ler pagamentos vinculados a um `shopId` alheio.

---

### 3. Falta de verificação de assinatura HMAC no webhook do Mercado Pago
- **Severidade:** MÉDIO
- **Arquivo afetado:** `functions/src/payment/mercadoPagoWebhook.ts`
- **Comportamento vulnerável:** A Cloud Function HTTP `mercadoPagoWebhook` aceita requisições `POST` sem validar o cabeçalho de assinatura do webhook do Mercado Pago (`x-signature` / secret de validação).
- **Impacto possível:** Embora a função consulte a API do Mercado Pago (`paymentClient.get({ id: paymentId })`) antes de atualizar o estado de assinatura no Firestore — o que impede a ativação ilegítima com IDs não pagos —, um atacante pode enviar enxurradas de requisições `POST` com IDs arbitrários. Isso pode causar negação de serviço (DoS), esgotamento de cotas de execução do Firebase Functions e custos excessivos com chamadas externas de API.
- **Correção recomendada:** Validar a assinatura HMAC no cabeçalho `x-signature` utilizando uma chave secreta configurada no Firebase Secrets Manager (`defineSecret`), rejeitando requisições sem assinatura válida antes de efetuar chamadas à API do Mercado Pago.
- **Cabe teste de regressão:** Sim. Teste unitário na Cloud Function verificando que requisições sem assinatura válida retornam erro de autorização (`401/403`).

---

### 4. Endpoints de geocodificação sem autenticação Firebase (`geocode` e `reverseGeocode`)
- **Severidade:** MÉDIO
- **Arquivo afetado:** `functions/src/geo/geocode.ts`
- **Comportamento vulnerável:** As funções `geocode` e `reverseGeocode` expõem endpoints HTTP públicos sem exigir o token de autenticação Firebase (não verificam o cabeçalho `Authorization: Bearer <idToken>`).
- **Impacto possível:** Qualquer usuário não autenticado na internet que conheça a URL do endpoint pode usá-lo como um proxy gratuito para realizar consultas na API do Google Maps, consumindo a cota e gerando custos associados à chave `GOOGLE_GEOCODING_KEY`.
- **Correção recomendada:** Adicionar a verificação do Firebase ID Token (`admin.auth().verifyIdToken(idToken)`) no início do tratamento das requisições de geocodificação, exatamente como é feito em `createPixCharge`.
- **Cabe teste de regressão:** Sim. Teste unitário garantindo que chamadas não autenticadas às funções de geocodificação retornam `401 Unauthorized`.

---

### 5. Ausência de validação de limites nos parâmetros do proxy de geocodificação
- **Severidade:** BAIXO
- **Arquivo afetado:** `functions/src/geo/geocode.ts` (linhas 72–78)
- **Comportamento vulnerável:** A função `reverseGeocode` checa apenas a presença de lat/lng (`lat == null || lng == null`), mas não valida o tipo numérico e o intervalo geográfico (`-90 <= lat <= 90` e `-180 <= lng <= 180`).
- **Impacto possível:** Envio de dados malformatados ou fora dos limites pode causar erros inesperados na integração com a API do Google Maps.
- **Correção recomendada:** Adicionar validação de tipo e intervalo numérico para `lat` e `lng`.
- **Cabe teste de regressão:** Sim. Teste unitário verificando retorno `400 Bad Request` em payloads com coordenadas inválidas.

## Verificação de Outras Superfícies de Segurança

### A. Credenciais e Histórico do Git
- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Chaves de API e segredos críticos (como `MP_ACCESS_TOKEN` e `GOOGLE_GEOCODING_KEY`) utilizam o Firebase Secrets Manager (`defineSecret`). O repositório não contém arquivos de credenciais commitados (`google-services.json`, `.env`, ou chaves privadas).

### B. Logs e Proteção de Dados Sensíveis (PII)
- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Inspeção dos logs (`logger.info`, `logger.error`) em `src/` e `functions/src/` confirma que nenhum e-mail, telefone, token FCM bruto, senha ou payload de pagamento é impresso nos logs. Apenas IDs de entidade (`shopId`, `appointmentId`, `customerUid`) são registrados para fins de depuração.

### C. Armazenamento Local no Dispositivo Móvel
- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** O `AsyncStorage` é utilizado no aplicativo exclusivamente para persistir a preferência de tema da UI (`dark` / `light`). Nenhum token de acesso, credencial ou dado pessoal é mantido em armazenamento local inseguro.

### D. Ativação de Assinaturas e Fluxo de Pagamento
- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** A confirmação e ativação de assinaturas são efetuadas exclusivamente via backend (Cloud Function `mercadoPagoWebhook`) usando o Firebase Admin SDK. O aplicativo cliente não possui permissão de escrita direta sobre o status de assinatura ou datas de expiração (`activeUntil`). O valor do plano é fixado no servidor (`PLAN_AMOUNT = 89.0`), impedindo manipulação de preço pelo cliente.
